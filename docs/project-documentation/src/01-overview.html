What it does today

  • Sells. A CRM of every contact, with duplicate detection across every email and phone on file, and a Contact stages board from first contact to signed or lost.
  • Signs. Contract signed records the system sold and creates the project in one step, signed on screen or sent through PandaDoc; change orders are signed the same way and update the contract value.
  • Delivers. A seven-stage pipeline (Survey to Complete, plus Hold and Cancelled) with a form per stage holding the solar facts each stage turns on; a project cannot advance with paperwork missing — and, where the admin allows, advances by itself when nothing is.
  • Tells everyone. Fifty-five kinds of notification — permit approved, equipment delivered, install tomorrow not ready, your project moved — for homeowners, PMs, admins, reps and dealers, in the app, by email and by push, each with a switch.
  • Serves the homeowner. A plain-language portal and iOS/Android app: current stage and its typical duration, chat with their PM, uploads, push, and a rating after every stage.
  • Serves dealers, measures and answers. A dealer portal, a live dashboard, a report builder with Excel/CSV export, and Ask SolarFlow, an AI assistant answering from live data.
  • Reads, drafts and briefs. Every stage attachment is read into the form with evidence for a person to accept; homeowners' messages get a drafted reply; each PM gets a morning briefing; and anything the automation is unsure of lands in one exceptions queue.

Where it stands

The delivery pipeline, portals, mobile app, chat, feedback, dashboard, reports and the core CRM are built and covered by automated tests. The platform runs on plain PostgreSQL (Neon) and Vercel. The application applies its own database migrations from Admin → Database, so no SQL console is needed.

The honest position on AI

Five AI capabilities are live: Ask SolarFlow answers; the document reader reads stage attachments into the forms; reply drafts answer homeowners; the morning briefing writes each PM's day; and evidence-based auto-advance moves complete projects on. Each defaults to proposing rather than acting, and needs ANTHROPIC_API_KEY and an admin's switch to do more. What it does not yet do: read the utility bill on the deal, watch permit portals, take actions on request, or send SMS. Chapters 12, 16–17 and the separate AI & Automation Blueprint set out the rest.

The three most valuable next steps

  1. Switch it on. Set CRON_SECRET and the Anthropic key, apply migrations 004600–004800, and review the exceptions queue for a week; then turn on auto-apply, auto-advance for Inspection & PTO and Permits, and auto-send for routine replies (chapters 12 and 14).
  2. Connect the outside world. Permit and interconnection portals, the utility bill on the deal, lenders and monitoring platforms: each becomes documents and statuses the reader and the notifications already know how to handle (chapter 16).
  3. Close the loop on speed-to-lead. Instant, automated first response and appointment booking on every new contact. This is the single largest driver of close rate in residential solar (chapter 19).

Design principles the code follows

One source of truth

The Deals board is the Pipeline's own board over the projects deals became, not a copy. The contact's stage lives on the person. Field lists such as the intake registry are data, and they drive the forms, the save allowlists and the signing popup together.

Rules in the database

A won deal cannot be un-won, a signed contact with a project cannot be moved, a customer cannot read an internal chat note, and a dealer cannot see another dealer's project. All of this is enforced by triggers, security-definer functions and policies, not by the UI.

Atomic business steps

Signing records the system, moves the contact and creates the project in one statement. Deal-to-project conversion carries the documents across. A refusal leaves nothing half-written.

Degrade, never break

If the database is a migration behind, screens show which file is missing rather than crashing. /api/health reports the build, the database endpoint and every migration.

Database migrations

The schema is 49 ordered migration files (appendix A). Each is idempotent and guarded: it refuses, with the name of the file to run first, if a prerequisite is missing. The deployment carries its own migration files, and Admin → Database shows which are applied and applies the rest with one button, each file in its own transaction, recording what ran. Detection works by probing for what each file creates, including the shape of a function where the name alone is ambiguous.

Lesson built in

A migration that has shipped is never edited again; a correction always goes in a new file. The one time an applied file was rewritten, databases that already had it could not see the change, which is why the signing function now lives in its own file (004100) and is detected by what it returns.

Users, roles & access

Seven roles. Each lands on its own home screen, and each sees exactly what the database's row-level security allows. Hiding a button is never the protection.

Sign-in

Three front doors: staff, dealer and homeowner. Behind them is one login function, one validation path, one rate limiter and one role router. Ten failed passwords lock an account for ten minutes. Password recovery and invitations use 7-day, single-use links. Admins can set a password with force-change-on-first-login. Homeowners are auto-invited when their project is created.

Access that needs no login

LinkGrants
/u/<token>Uploading photos to one project, for a crew member or homeowner without an account. The token is hashed at rest, expires within 7 days and can be revoked, and no session is ever created.
/r/<token>Recording one stage rating from the email's five faces. The score is saved before the page renders, because requiring a login loses most responses.
