Chapter 7 · Module catalogue

Dealer & partner modules

Dealers bring sales. They see their own book, submit leads and follow their commissions, all read-only over data the project team enters, and scoped in the database so one dealer can never see another's.

M13Dealer portalLive

Migration 001900 · /dealers, /dealers/projects, /dealers/leads, /dealers/commissions · sign-in door: dealer

  • Dashboard: four stat cards, projects by stage, recent activity ("what is moving") and needs attention ("what is stuck").
  • Projects: their company's projects and each project's detail, with per-field dealer visibility set by the admin, so a dealer sees exactly the fields the business chooses to show.
  • Leads: the dealer submits a lead into a queue the PM reviews. It never creates a project directly. The dealer sees the status and the resulting project once converted.
  • Commissions: their commission lines per project.
  • The only dealer write paths are lead submission and their own account settings.
M14Dealer companies & commissionsLive

Migration 002000 · Admin → Dealers · /api/projects/[id]/commission

Each dealer company has a full record covering identity, commercial terms, portal behaviour and commission defaults. A trigger seeds a new project's commission from those defaults. Names are unique regardless of case and spacing (so "SunPro Energy LLC" and "sunpro energy llc " are caught at creation), and every change is audited. A company with projects or leads cannot be deleted by any code path, because the foreign keys refuse it. Dealer users are linked to companies, and a company can be created inline from the project form.

M15Lead review queueLive

/leads (admin, ops) · /api/leads

Everything dealers have submitted, with Review, Convert and Decline actions. Converting creates the client and the project prefilled from the lead, links it back for the dealer, and auto-invites the homeowner with a set-password link. Since the CRM foundation, dealer submissions also live on as deals, keeping their attribution. The original leads view still answers for anything that reads it.

Chapter 8 · Module catalogue

Homeowner experience modules

The homeowner is kept informed without having to phone: where their project is, how long this part usually takes, what is needed from them, and a direct line to their project manager.

M16Customer portalLive

Migrations 002300, 003100 · /portal, /portal/project, /portal/documents, /portal/photos, /portal/messages, /portal/more

  • Shows the stage they are in, not the seven they could be in: one clear card with progress, the typical duration of the current stage ("Typical 15–30 days") and what is up next ("Up next: Design · 7–10 days"). This answers the question behind most status calls before anyone picks up the phone.
  • Plain language: one admin-editable mapping layer turns internal values ("ICA Status: Applied") into homeowner wording. A raw dropdown value is never shown.
  • Four genuine actions land as requests in the PM's queue rather than writing stage data: give availability, ask a question, update contact details, send a document.
  • An optional PM-set completion estimate (no estimate is better than a wrong one), a "call my PM" card, and customer-visible documents and photos with ZIP download.
  • Typical durations are configuration, not code: they are seeded from the business's own history once enough projects have completed.
  • Dark mode, installable, mobile-first.
M17Customer managementLive

Migration 002400 · /admin/customers, /admin/people, /api/customers/*

The customer is a person and the project is a job: one client can carry several projects. This module finds, corrects, merges and controls portal access for existing records. It covers search, merging duplicates with a field-by-field choice, archiving, and anonymising for data-deletion requests. Portal access is managed here too: send an invite, set or reset a password, revoke. A customer with projects or leads cannot be deleted, and destructive operations run through admin-checked database functions.

M18Customer mobile app (iOS & Android)Live

Migration 002500 · Capacitor projects in /android, /ios · GitHub Actions: Build Android app, Build iOS app · docs/mobile-store-submission.md

  • An installable portal with six tabs (Home, Messages, Project, Docs, Photos, More). It adds camera upload, offline support and native push. It uses one database, one API and one set of security rules, with nothing copied or synced.
  • Push for stage changes, PM asks, chat and install reminders 48 and 24 hours before. It respects per-customer notification preferences, and every delivery is recorded, keeping pushes under ten per project in a measurable way.
  • PM asks: the PM requests something (a photo of the electrical panel, a signature, a date) and the customer answers in the app.
  • The store app contains the customer portal and nothing else. Builds refuse a pinned deployment URL (which would never update), and in-app account deletion meets store rules.
  • A debug APK is built from the GitHub website with no signing setup. Signed release bundles are built when the signing secrets are present.
M19Project chat & Messages inboxLive

Migration 002900 · /projects/[id]/chat (+ print view), /messages, /portal/messages

  • One thread per project between the PM and that project's customer, kept on the project record for the life of the job.
  • Internal notes are walled off in the database: a customer's query cannot return one, and a customer cannot create one. In the UI they are a separate tab in a different colour.
  • Messages is the PM's global inbox across all projects, unread first then newest, so a message from three days ago is never buried.
  • Canned replies, flags, read tracking, unread badges on pipeline cards, and a print view for the record.
  • Notifications: push if the customer has the app, otherwise email. Quiet hours hold messages between 9pm and 8am local and deliver them in the morning rather than dropping them. PMs get a per-message email if they opt in, otherwise a twice-daily digest of unanswered messages.
M20Stage feedback & follow-upsLive

Migration 003200 · in-portal sheet, email faces via /r/<token>, /tasks (Follow-ups), /feedback (verbatim log)

  • A one-tap rating the moment each stage completes, six or seven times per project instead of one survey at the end, so you learn which stage lost the customer while it can still be fixed.
  • The score is saved on tap. Reasons ("chips") and a comment are optional and attached separately. Every score offers the comment box.
  • Email fallback: if a rating is not answered in the app within 24 hours, one email with five clickable faces goes out. Clicking records the score immediately, with no login.
  • A low score opens a follow-up task (Follow-ups, oldest first) that stays on the pipeline card until someone closes it with a note.
  • The verbatim log lists every comment with score, stage, date and chips, filterable and searchable.
