Chapter 5 · Module catalogue

Platform modules

The layer everything else stands on: the database and how it keeps itself current, who can sign in, what each role may see, where files live, and the record of who did what.

M01Database & self-applying migrationsLive

Migrations 000000–000400, db-migrations/db-apply, Admin → Database, /api/health

Plain PostgreSQL with no vendor-specific features, so it runs on Neon, any managed Postgres or a local install. The app role connects through a pooled connection and switches to an authenticated role per request, carrying the user's identity as claims that the security policies read.

Screens
Admin → Database: every migration the deployment carries, which are present, and one Apply button that runs the missing ones in order, each in its own transaction, recording them in schema_migrations and reporting PostgreSQL's exact words on any refusal.
Health
/api/health: build commit, which environment variables are set, a masked database endpoint (so two deployments can be compared), a branch marker, the database connection result and the list of migrations the database is behind.
Safety
Every migration is idempotent and guarded. When a module is missing, screens show a notice naming the file rather than failing, and errors name the real cause. SQL bundles in db/dist remain for console use.
M02Authentication & sign-inLive

Migrations 001000, 002600, 002700, 003000 · docs/auth.md

A complete auth engine inside the database, replacing Supabase Auth. Credentials, sessions and one-time tokens are reachable only through security-definer functions; the application role has no direct access to the tables.

  • bcrypt passwords (cost 12); sessions are opaque 256-bit tokens in an httpOnly cookie, with only the SHA-256 stored; 7-day lifetime, revocable server-side.
  • Lockout after 10 consecutive failures, for 10 minutes. One sign-in function behind three doors (staff, dealer, homeowner), with role-based routing.
  • Invitations and password recovery by 7-day single-use links, for every role including homeowners. Admin-set passwords can force a change at first login. Every password field has a show/hide control.
M03Roles & row-level securityLive

Migrations 000300, 000600, 000800, 000900, 003300, 004200 · docs/rls-matrix.md

190 policies across 88 tables implement the role contract in chapter 4. Functions lose the default public execute right, and sensitive writers run as security-definer with explicit role checks. The finance role reads only whitelisted columns through a view. Sales reps see a deal's project exactly when they can see the deal: the policy asks the deals table rather than repeating its rules.

M04Files & documentsLive

Migrations 000700, 001100 · lib/storage, /api/files, /api/documents, /u/<token>

Private buckets (drawings, PDF deliverables, photos) with the bytes stored beside their metadata in Postgres. Documents are filed against a deal before signing and gain the project link at conversion, so nothing is uploaded twice. Customers see only customer-visible documents. Crews and homeowners can upload photos through time-limited, revocable links without an account.

M05Audit & activity logLive

Migration 000500 (+ kinds, deal/client links in 003400) · Admin → Activity log

One shared writer that every module calls. It records actor, role, action, entity, context, the kind of activity (call, email, SMS, meeting, note, form, stage move, field change, login, system) and links to project, deal and client. Rows cannot be edited. Stage moves, signings, project deletions, merges and admin actions are all logged; password values never are. The same log is the contact's Activity tab and the deal timeline.

M08Hold, Cancel & CompleteLive

Migrations 001500, 001600

Any project can go on Hold or be Cancelled from any stage, bypassing validation, because a customer pulling out must never be blocked. The move needs a reason from a list and notes. Hold reasons: customer request, finance pending, weather, access issue, awaiting documents, site issue, other, with an expected resume date. Cancellation reasons: customer cancelled, failed credit, site not viable, permit denied, duplicate, competitor, other, with refund/clawback and equipment-return flags. The origin stage is stored, so Resume and Reinstate (admin-only) restore the project exactly. Held and cancelled projects leave active counts but are never deleted.

M09Projects & project detailsLive

Migrations 001700, 001800, 002100 · /projects/new, /projects/[id]

The New Project form and the project record: customer, site address, dealer, sales rep, jurisdiction, utility, and a system specification (system type, module type and quantity, inverter type and quantity, battery type and quantity, system size) plus financing (cash or financing, company, notes, estimated completion shown to the customer). Equipment and financing values come from admin-managed lists stored by ID, so fixing a typo in a module name fixes it everywhere. The project page has panels for customer, details, system specification, financing and commission, a stepper to each stage form, and the header actions (hold, cancel, resume, reinstate, delete).

M11Analytics dashboardLive

Migration 002800 · /dashboard (admin, ops, finance)

One full-width scrolling page in four bands, densest at the top. Nothing is a hand-maintained list: every figure is a live aggregate grouped by PM, dealer and stage, so a new hire's projects appear the first time one is assigned. Stat cards stream first and charts fill in behind them. Per-stage ageing thresholds live in the database (stage_thresholds) so they can be re-tuned without a release. A quarter is the default period, sample sizes are shown plainly, and a count and its share are shown as two separate figures.

M12Report builderLive Schedules

Migration 002200 · /reports, /reports/builder

Drag-and-drop reports opened blank, from a template or from a saved report. A report is a JSON definition, never SQL: the generator builds a parameterised query from whitelisted columns, so nothing a user writes is ever executed. The field library is filtered to what the role may see. Output is preview, print, Excel (.xlsx) or CSV. Reports can be private, shared with a role or shared with named users, and every run is recorded.

Open item

The data model stores report schedules, but nothing yet runs them on a timetable. See chapter 14.
